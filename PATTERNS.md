## Methods

| method | meaning |
|---|---|
| db | upstream BG pattern already matched uniquely in Torment and was confirmed by other evidence |
| vote | masked instruction-window voting (port2.py) + context scoring (decide.py) |
| fmap | global function map BG->PT (signatures, call-graph propagation, link order) (globalmap*.py) |
| align | instruction alignment inside the mapped function (final.py) |
| local | anchors on neighbouring mapped calls / caller votes inside the mapped function (local.py) |
| gxref | data target voted over all BG RIP-relative references (gxref.py) |
| manual | hand review of BG/PT disassembly (manual.json, show.py/rv.py) |

Confidence: **high** = two independent methods agree or exact code match; **medium** = one strong method, or reviewed by hand with PST-specific code differences; **low** = best available guess, revisit in phase 4/5.

Scope: every entry was located and its surrounding code compared (normalized instructions, call targets, data references). Hook *bodies* (registers, stack offsets, restore sizes) were not re-validated one by one: PSTEE often uses other registers and struct offsets (e.g. CDerivedStats +8, CGameSprite fields shifted), so each EEex hook must be checked when the Lua patches are ported (phase 5); known cases are listed below.

Addresses are RVAs in Torment.exe v3.2.2.0 (image base 0x140000000). For rel32 entries the address is the final target.
